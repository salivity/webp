Next.js WebP Image Optimization Explained

Next.js optimizes static and dynamic images by leveraging its built-in Image Optimization API alongside modern browser capabilities. By using the next/image component, Next.js intercepts image requests, inspects client support via HTTP headers, converts standard formats like JPEG and PNG into modern WebP format on demand, and caches the converted assets for subsequent requests.

The Role of the Image Component

The foundation of this optimization pipeline is the next/image component, an extension of the standard HTML <img> element. When you implement this component, Next.js does not serve the raw source file directly to the browser. Instead, it rewrites the image source URL to point to an internal optimization endpoint: /_next/image.

This endpoint receives parameters containing the original image path, the target width, and the target image quality.

HTTP Content Negotiation

Next.js automatically determines when to serve WebP through standard HTTP content negotiation. When a browser requests a page, it includes the Accept request header, listing the MIME types it can parse (such as image/webp or image/avif).

When the request hits the /_next/image route:

  1. The Next.js server reads the incoming Accept header.
  2. If the browser supports WebP (which nearly all modern browsers do), Next.js prioritizes converting the image into WebP format over legacy formats like PNG or JPEG.
  3. The server sets the appropriate Content-Type: image/webp in the response headers.

On-Demand Server-Side Transformation

Next.js performs transformations dynamically on demand rather than converting every image during the build step. This prevents build times from ballooning as an application grows.

  • Processing Engine: Next.js uses sharp, a high-performance Node.js image processing library, in production environments. If sharp is not installed, it falls back to a WebAssembly-based implementation.
  • Resizing and Encoding: When a request is received, the optimization engine resizes the source file to match the requested device size and encodes the output into WebP with default quality compression (typically 75%).

Handling Static vs. Dynamic Assets

Next.js treats static and dynamic images identically during the transformation phase, but prepares them differently:

  • Static Assets: When an image is imported directly from the local filesystem (e.g., import profilePic from './profile.png'), Next.js automatically calculates the file's intrinsic width, height, and aspect ratio at build time. This data is passed directly to the optimizer to prevent Cumulative Layout Shift (CLS) before the WebP is generated.
  • Dynamic Assets: When referencing remote images via absolute URLs, you must declare permitted domains or patterns in next.config.js under remotePatterns. When requested, Next.js downloads the external image upstream, applies the same sharp conversion to WebP, and serves it through the local optimization endpoint.

Caching and Delivery

To ensure low latency and minimize CPU load, Next.js caches the converted WebP images after the initial transformation:

  1. The first request triggers the fetch, resize, and WebP encoding.
  2. The optimized WebP file is stored locally in the .next/cache/images directory (or in external storage when hosted on platforms like Vercel).
  3. Subsequent requests for the same image, dimension, and format are served directly from the cache with an HIT status.
  4. Next.js assigns appropriate Cache-Control headers (defaulting to a long expiration) to allow CDNs and browser caches to store the optimized WebP asset.
