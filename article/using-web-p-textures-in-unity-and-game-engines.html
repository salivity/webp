Using WebP Textures in Unity and Game Engines

Game engines like Unity provide specialized pipelines to import, process, and package WebP image assets, taking advantage of their high compression efficiency to reduce source repository sizes and data transfer payloads. While WebP is an effective container for asset storage and web distribution, real-time game engines do not upload WebP data directly to the GPU. Instead, the engine decompresses the WebP file during the import or build pipeline and re-encodes it into GPU-native texture compression formats such as ASTC, BC, or ETC to maintain optimal rendering performance in memory.

The WebP Import Process

When a developer imports a .webp file into Unity or similar game engines, the engine's asset pipeline initiates an import worker to parse the file format. Unity natively supports WebP across modern versions, reading both lossy and lossless variants, including transparency channels and embedded color profiles.

Upon ingestion, the engine uses an underlying decoder (typically derived from Google's libwebp library) to decompress the image into an uncompressed raw pixel array, such as standard 32-bit RGBA. This raw data is cached locally within the engine's internal cache—such as Unity’s Library folder—rather than leaving the WebP file to be read continuously from disk. This ensures that subsequent operations within the editor do not incur repeated decompression overhead.

The Difference Between Storage and GPU Compression

A common misconception is that importing a WebP file results in WebP data residing in system RAM and VRAM during gameplay. General-purpose image formats like WebP, JPEG, and PNG use variable-length entropy encoding. These formats are designed to minimize file size on disk, but modern GPUs cannot read them directly because they do not support random access to individual texels. To display an image encoded this way, the GPU would need to decompress the entire image into uncompressed VRAM, consuming large amounts of memory bandwidth.

To resolve this, modern game engines use block-compression algorithms (such as BC7 for PC/consoles, or ASTC and ETC2 for mobile devices). Block compression divides the image into fixed-size blocks (e.g., 4x4 pixels) that can be randomly accessed and sampled in hardware on the fly without decompressing the rest of the texture.

Packaging and Build-Time Compression

During the project build step, game engines process all texture assets according to the target platform’s compression settings:

  1. Decompression: The engine pulls the raw, uncompressed pixel data generated from the original WebP source from its local cache.
  2. Mipmap Generation: If enabled, the engine calculates mipmaps (downscaled representations of the texture) directly from the raw pixel data.
  3. Hardware Encoding: The engine compresses the base texture and all mip levels into the chosen target format (e.g., ASTC for iOS/Android, BC7 for DirectX/Vulkan).
  4. Serialization: The resulting block-compressed texture data is packed into engine asset bundles, streaming archives, or platform-specific package files (such as .apk or .pak).

At runtime, the engine loads the block-compressed data straight into VRAM, completely bypassing the original WebP representation.

Runtime Loading and Web Streaming

When WebP is used outside the static build pipeline—such as downloading assets dynamically over HTTP or streaming textures in WebGL builds—engines handle the asset differently. Unity provides APIs such as UnityWebRequestTexture and ImageConversion.LoadImage to process WebP data in memory at runtime.

When a WebP file is downloaded dynamically:

  • The engine allocates a CPU memory buffer to receive the raw file bytes.
  • A native background worker decompresses the WebP stream into a raw RGBA byte buffer.
  • The engine uploads the uncompressed texture data to the GPU.
  • If runtime crunching or dynamic compression is configured, the engine performs a fast, software-based compression before uploading, though this incurs a CPU performance cost.

Best Practices and Considerations

Using WebP as a source asset in game development offers distinct advantages alongside technical trade-offs:

  • Repository Size: Using WebP reduces repository sizes and asset download times for distributed development teams compared to uncompressed TGA or large PNG files.
  • Generation Loss: Avoid importing lossy WebP files into an engine if the asset will subsequently be compressed into a lossy GPU format like BC1 or ASTC. "Double compression" introduces severe compression artifacts and color banding. Lossless WebP is the preferred source format.
  • Build Times: Because WebP must be decoded before being re-encoded into platform-specific formats, using thousands of WebP source files can increase clean project build times compared to simpler, fast-reading source formats like uncompressed TGA.
