WebP MIME Type as octet-stream: Causes and Fixes

When a web server is misconfigured to serve WebP images with the application/octet-stream MIME type instead of image/webp, web browsers are unable to recognize the files as standard inline graphics. This article explores how browsers react to this misconfiguration—often resulting in broken image icons or forced file downloads—the performance and SEO issues it creates, and the exact server-level changes required to resolve it.

Why the MIME Type Matters

The Multipurpose Internet Mail Extensions (MIME) header tells a client how to process and render a requested file. When a browser requests an image, it relies on the Content-Type response header to identify the correct decoder. The standard MIME type for WebP graphics is image/webp.

If a server does not recognize the .webp file extension, it defaults to application/octet-stream. This is a generic fallback designating arbitrary binary data with no specific rendering rules.

How Browsers Handle WebP as octet-stream

When a server sends a WebP asset with a Content-Type: application/octet-stream header, client behavior depends on how the resource was requested:

  • HTML <img> Tags: Most modern browsers (such as Chrome, Firefox, Safari, and Edge) will refuse to parse the binary stream as an image. Because the declared type is not an image MIME type, the browser halts rendering and displays a broken image placeholder or an empty space, disrupting the visual layout.
  • Direct URL Navigation: If a user navigates directly to the image URL (e.g., example.com/photo.webp), the browser will not display the image on the screen. Instead, it treats the resource as an unknown file download, immediately triggering a "Save As" dialogue.
  • CSS Backgrounds: When referenced via background-image: url(...), the stylesheet parser typically discards the resource entirely, leaving the background blank or falling back to an underlying color.
  • MIME Sniffing Variations: While some browsers occasionally attempt content sniffing to detect image signatures within the file payload, security policies like X-Content-Type-Options: nosniff strictly enforce the server-provided header, guaranteeing failure.

Impact on Website Performance and SEO

Serving WebP files as binary streams directly damages user experience and site metrics:

  • Visual Degradation: Key UI elements, banners, and product photos fail to load, leading to high bounce rates.
  • Cumulative Layout Shift (CLS): Missing images cause page elements to shift erratically as the layout engine calculates page dimensions without rendered media.
  • Search Engine Crawling: Search engine bots may classify the assets as downloadable binary files rather than visual content, preventing the images from being indexed in search results.

How to Fix the Misconfiguration

To resolve this issue, the server must be configured to map the .webp extension to image/webp.

Nginx

Ensure the image/webp webp; directive exists inside /etc/nginx/mime.types, or add it manually to your server configuration block:

types {
    image/webp webp;
}

Apache

Add the appropriate type definition to your httpd.conf or your local .htaccess file:

AddType image/webp .webp

Microsoft IIS

Open the IIS Manager, navigate to the MIME Types feature for the website, and add:

  • File name extension: .webp
  • MIME type: image/webp

Once configured, verify the fix using curl -I https://example.com/image.webp in your terminal to confirm that the Content-Type header returns image/webp.
