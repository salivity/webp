WebP Canvas Decoding Polyfills in JavaScript

Before WebP achieved universal browser adoption, developers relied on JavaScript-based polyfills to decode and display the format in non-supporting browsers such as Internet Explorer, older versions of Safari, and early Firefox releases. These solutions worked by fetching the binary WebP data, parsing the VP8 bitstream using JavaScript ports of native decoders, and rendering the resulting raw pixel data directly onto HTML5 <canvas> elements. This article examines the prominent historical libraries that implemented this technique and how their canvas-rendering pipelines functioned.

libwebp via Emscripten

The foundational technology behind most early canvas-based WebP polyfills was Google’s native reference library, libwebp, compiled into JavaScript using Emscripten. Because WebP is based on the VP8 video keyframe format, writing a performant decoder purely in hand-written JavaScript was impractical.

By compiling the official C decoder into asm.js or raw JavaScript, developers could pass binary arrays directly into the compiled memory heap, execute the C-level decoding logic in the browser's JavaScript engine, and receive raw RGBA pixel arrays.

webpjs

One of the earliest and most widespread turnkey implementations was webpjs (developed around 2011–2012 by Dominik Homberger). It packaged a lightweight, Emscripten-compiled VP8/WebP decoder into a drop-in script designed to handle DOM replacement automatically.

webpjs operated through the following steps:

  1. Scanning the document for <img> elements or CSS background declarations referencing .webp files.
  2. Intercepting the source URL and requesting the file as binary data via XMLHttpRequest with overrideMimeType('text/plain; charset=x-user-defined') or responseType = 'arraybuffer'.
  3. Passing the binary payload to the compiled decoder to produce an unpacked array of RGBA bytes.
  4. Generating a hidden or replacement <canvas> element matching the image's dimensions.
  5. Painting the decoded bytes to the canvas context using putImageData(), or converting the canvas to an inline PNG Data URL (canvas.toDataURL('image/png')) to assign back to the image tag's src attribute.

webp-hero

In later years, prior to Apple's implementation of WebP in Safari 14, webp-hero emerged as the standard modern polyfill. Developed by Chase Moskal, webp-hero modernized the canvas polyfill approach by leveraging WebAssembly where supported, while providing a pure JavaScript asm.js fallback for older targets like Internet Explorer 11.

webp-hero offered an API (WebpMachine) that developers could invoke programmatically or apply globally across the DOM. It decoded WebP images through a WebAssembly build of libwebp, extracted the raw image buffer, drew the buffer to an in-memory canvas context, and replaced the original elements' sources with PNG object URLs or Data URIs.

The Standard Decoding and Canvas Pipeline

Regardless of the specific library used, the technical execution pattern for canvas-based WebP decoding remained consistent:

  1. Binary Ingestion: WebP assets were retrieved asynchronously using fetch or XMLHttpRequest with an arraybuffer response type.
  2. Buffer Allocation: The array buffer was copied into the decoder’s memory space (often Module.HEAPU8 in Emscripten environments).
  3. Bitstream Decompression: The decoder's WebP decoding function (such as WebPDecodeRGBA) parsed the header, unpacked the VP8/VP8L payload, and returned a pointer to the decoded RGBA buffer along with the image's width and height.
  4. Canvas Rasterization: 
    var canvas = document.createElement('canvas');
canvas.width = decodedWidth;
canvas.height = decodedHeight;
var ctx = canvas.getContext('2d');
var imageData = ctx.createImageData(decodedWidth, decodedHeight);
imageData.data.set(new Uint8ClampedArray(decodedRgbaBuffer));
ctx.putImageData(imageData, 0, 0);
  5. DOM Injection: The library replaced the target <img> element with the <canvas> node directly, or extracted a standard data URI via canvas.toDataURL() to preserve standard image tag semantics.

Technical Limitations and Retirement

While functional, canvas decoding polyfills introduced noticeable CPU overhead and memory pressure, as decoding occurred entirely on the browser's main JavaScript thread. Frame rates could stutter during page load, and animated WebP files caused severe performance drops. As native support was finalized across Firefox (version 65), Edge (version 18), and Safari (version 14/iOS 14), these polyfills were phased out in favor of native HTML <picture> elements with progressive fallbacks.
