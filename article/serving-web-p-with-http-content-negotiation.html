Serving WebP with HTTP Content Negotiation

Server-side content negotiation allows web servers to automatically serve modern, highly compressed WebP images to browsers that support them, while delivering standard formats like JPEG or PNG to browsers that do not, all without altering the image URL. This process relies on the client signaling its capabilities through the HTTP Accept request header, enabling the server to make dynamic routing decisions before delivering the payload and ensuring optimal performance and compatibility.

The Role of the HTTP Accept Header

When a web browser requests an asset, it sends several HTTP headers detailing its capabilities. Modern browsers that support WebP include the MIME type image/webp inside the Accept request header.

A standard image request header typically looks like this:

Accept: image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8

This string informs the server that while the client will accept standard image formats, it explicitly supports and prefers optimized formats like WebP. If a browser does not support WebP, the string image/webp will be absent from this header.

The Server-Side Negotiation Mechanism

Once the request reaches the server, content negotiation proceeds through four main steps:

  1. Inspection: The server intercepts the request for an image resource (e.g., /images/photo.jpg) and reads the Accept header.
  2. Evaluation: The server evaluates whether image/webp exists within the Accept string and verifies whether an equivalent WebP file (e.g., /images/photo.webp) exists on disk or can be generated dynamically.
  3. Internal Rewrite: If both conditions are met, the server internally rewrites the request path to deliver the WebP file. If the header lacks WebP support or the WebP version is missing, the server defaults to the original format (JPEG or PNG).
  4. Header Modification: The server sets the outgoing Content-Type header to match the payload actually being sent (e.g., Content-Type: image/webp).

Because this substitution happens internally on the server, the client's browser maintains the original resource URL in the DOM, eliminating the need for client-side JavaScript or HTML <picture> elements.

The Critical Role of the Vary Header

When serving different file formats from the same URL, caching layers—such as intermediate proxies, Content Delivery Networks (CDNs), and local browser caches—can inadvertently serve WebP files to unsupported clients.

To prevent this issue, the server must append the following header to every response:

Vary: Accept

The Vary: Accept header instructs caches to create separate cache keys based on the contents of the incoming Accept header. A request with Accept: image/webp will receive and cache the WebP version, while a request without it will receive and cache the JPEG or PNG version.

Server Implementation Patterns

Web servers implement this negotiation via configuration rules:

  • Nginx: Uses the map directive to inspect $http_accept. If it contains webp, Nginx assigns an internal variable to match the .webp extension and uses try_files to serve the modern file if it exists, falling back to the original if it does not.
  • Apache: Leverages mod_rewrite to evaluate the %{HTTP_ACCEPT} variable for image/webp alongside a RewriteCond to verify the .webp file exists on disk, silently rewriting the request while applying Header append Vary Accept.
