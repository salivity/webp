WebP Caching Issues Without Vary: Accept Header

Serving modern image formats like WebP at the same URL as legacy JPEG or PNG fallbacks relies on HTTP content negotiation. When a Content Delivery Network (CDN) fails to include the Vary: Accept header in its response, it treats requests from different browsers identically. This failure causes serious caching anomalies, resulting in either broken images on older browsers or lost performance optimizations on modern ones.

How Content Negotiation Works for WebP

Modern browsers explicitly state which image formats they support by sending an Accept request header. For example, a modern browser might send:

Accept: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8

Older browsers or specialized HTTP clients omit image/webp. An origin server configured for dynamic format delivery inspects this header. If image/webp is present, it returns WebP data; otherwise, it returns standard JPEG or PNG data.

The Critical Role of Vary: Accept

A CDN caches responses keyed primarily by URL. Without instructions to do otherwise, the CDN considers https://example.com/hero.jpg to have only one valid cached representation.

The Vary: Accept HTTP response header tells the CDN cache: "The response for this URL changes depending on the client's Accept request header. Store and serve separate cache entries based on that value."

The Two Major Caching Failures

When the Vary: Accept header is omitted, the CDN serves whatever format it cached first to every subsequent visitor, regardless of browser compatibility.

1. Cache Poisoning by WebP (Broken Images)

If a modern browser (such as modern Chrome or Safari) visits the page first:

  1. The CDN requests the image from the origin, passing along the browser's Accept: image/webp header.
  2. The origin responds with WebP image data.
  3. Because Vary: Accept is missing, the CDN caches this WebP payload under the standard URL key.
  4. An older browser, email client, or legacy application visits the same URL.
  5. The CDN delivers the cached WebP data.
  6. The legacy client cannot decode WebP, resulting in broken image icons, failed page rendering, or unexpected download prompts.

2. Cache Poisoning by Fallbacks (Degraded Performance)

If an older browser, search engine crawler, or bot that lacks WebP support visits the page first:

  1. The origin receives a request without image/webp in the Accept header and returns a heavier JPEG or PNG file.
  2. The CDN caches the legacy format under the generic URL key.
  3. Subsequent visits from modern browsers are served the cached JPEG or PNG instead of the optimized WebP.
  4. The site loses all bandwidth savings and visual load-time improvements associated with modern formats, leading to degraded Core Web Vitals.

Edge Caching Complications with Vary: Accept

While Vary: Accept prevents format mismatches, raw Accept headers vary widely between different browsers and versions. For example, one browser may request AVIF before WebP, while another specifies different quality weights (q=0.8 vs. q=0.9).

If a CDN strictly caches on the exact string of the Accept header, cache hit ratios plummet because each browser version generates a separate cache entry.

How to Fix the Problem

To prevent cache poisoning while maintaining high cache hit ratios:

  1. Emit the Header at Origin: Ensure the origin web server or image optimization service explicitly outputs Vary: Accept on all dynamic image responses.
  2. Normalize the Header at the CDN: Configure the CDN to normalize the Accept header at the edge. The CDN should inspect incoming requests and rewrite the internal cache key to simple variants (e.g., supports-webp=true vs supports-webp=false) before checking the cache.
  3. Use Explicit URLs Instead: Avoid dynamic content negotiation entirely by using the HTML <picture> element. By serving distinct URLs for each format (e.g., image.webp and image.jpg), each asset is cached under a unique key, eliminating the dependency on the Vary header.
