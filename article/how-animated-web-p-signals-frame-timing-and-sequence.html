How Animated WebP Signals Frame Timing and Sequence

Animated WebP files signal frame timing and sequence through a structured sequence of chunks defined by the Extended RIFF (Resource Interchange File Format) container specification. Rather than relying on external scripts, the WebP container embeds explicit playback parameters directly into dedicated metadata chunks. Frame ordering is strictly governed by the sequential appearance of Animation Frame (ANMF) chunks within the byte stream, while precise display duration is encoded as an individual millisecond timestamp inside each frame’s header.

The VP8X Header: Declaring Animation

Every animated WebP file begins with a standard RIFF header followed by an extended format chunk labeled VP8X. Within this chunk, a specific bit flag—the Animation flag (A)—is set to 1. This signals to the decoder that the file is not a static image and contains an animation stream made up of multiple sub-chunks, instructing the parser to look for global animation parameters and individual frame data.

The ANIM Chunk: Global Animation Parameters

Before individual frames appear, the container includes an ANIM chunk. This chunk defines the global canvas properties required for overall playback:

  • Background Color: A 4-byte value storing the default background color in BGRA order, used when clearing frames between renders.
  • Loop Count: A 16-bit integer determining how many times the animation cycles. A value of 0 indicates infinite looping, while any non-zero value defines an explicit repetition limit.

The ANMF Chunk: Controlling Frame Sequence and Timing

The sequence and timing of the animation rely entirely on consecutive ANMF (Animation Frame) chunks.

Frame Sequence

WebP does not use frame index numbers or timecodes to dictate playback order. Instead, the sequence is purely stream-oriented. The decoder renders frames in the exact linear order in which the ANMF chunks appear in the file.

Frame Timing (Duration)

Inside the header of each ANMF chunk is a 24-bit unsigned integer representing Frame Duration. This value specifies the display duration of that specific frame in milliseconds:

  • A value of 100 means the frame remains visible for 100ms (1/10th of a second).
  • Each frame can have an independent duration, allowing dynamic, variable frame-rate animations without redundant duplicate frames.
  • If a decoder encounters a duration of 0 ms, the behavior is implementation-dependent, but standard decoders typically enforce a minimum duration (commonly 10ms or 100ms) to prevent excessive CPU consumption.

Spatial Positioning and Canvas Disposal

In addition to timing, each ANMF chunk contains rendering metadata that affects how subsequent frames transition:

  • Frame X and Frame Y Offsets: 24-bit values defining the top-left coordinate where the current frame will be drawn on the global canvas. This allows for sub-frame updates (e.g., updating only a moving element rather than the entire canvas).
  • Frame Width and Frame Height: 24-bit dimensions defining the sub-canvas area of the frame.
  • Blending Method: A 1-bit flag determining whether the current frame blends with the underlying canvas using alpha transparency (0) or completely overwrites the target rectangle (1).
  • Disposal Method: A 1-bit flag indicating what happens to the frame area after its duration expires. The decoder can either retain the frame's content on the canvas (0) or dispose of it by clearing the area back to the canvas background color (1).

Frame Payload

Immediately following the control header of each ANMF chunk is the raw image payload for that frame, encoded as either a lossy VP8 chunk, a lossless VP8L chunk, or an ALPH (alpha) chunk paired with VP8. The decoder reads the header, waits for the specified duration, executes the disposal and blending instructions, and advances to the next sequential ANMF chunk until reaching the end of the file.
