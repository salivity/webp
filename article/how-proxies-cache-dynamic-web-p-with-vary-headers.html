How Proxies Cache Dynamic WebP with Vary Headers

Serving dynamic WebP images based on browser capabilities relies on content negotiation, requiring forward caching proxies to evaluate the HTTP Vary header correctly. This article explains how forward proxies interpret Vary: Accept directives, how they generate secondary cache keys, the challenge of cache fragmentation across different browsers, and the methods used to normalize requests to maintain high cache efficiency.

The Role of Content Negotiation and the Vary Header

When a web server dynamically serves modern formats like WebP to supported browsers while falling back to JPEG or PNG for others, it typically does so from the same URL. To notify intermediaries that the response body depends on the client’s capabilities, the origin server includes the following header:

Vary: Accept

A forward caching proxy acts as an intermediary between client devices (such as users within a corporate network) and the wider internet. Upon receiving a response with a Vary header, the proxy understands that it cannot use the URL alone to determine whether a cached asset can satisfy a future request.

Secondary Cache Key Generation

In a standard caching scenario, a proxy stores and retrieves assets using a primary cache key, usually consisting of the HTTP method and the request URL.

When a Vary: Accept header is present, the proxy constructs a composite or secondary cache key. This key incorporates:

  1. The HTTP request method (e.g., GET).
  2. The resource URL.
  3. The specific value of the client's Accept request header from the original transaction.

When a subsequent client requests the same image, the forward proxy inspects the incoming Accept header. It only serves the cached response if the new request's Accept header matches the one stored alongside the cached variant. If the header differs, the proxy treats the request as a cache miss, forwards it to the origin server, and stores a new variant corresponding to the new header value.

The Problem of Cache Fragmentation

While Vary: Accept preserves correctness by preventing unsupported browsers from receiving WebP images, it frequently degrades cache efficiency in forward proxies due to header diversity.

Different browsers and versions send varied Accept strings for image requests. For example:

  • Chrome: image/avif,image/webp,image/apng,image/svg+xml,image/*,*/*;q=0.8
  • Firefox: image/avif,image/webp,*/*
  • Safari: image/webp,image/png,image/svg+xml,image/*;q=0.8,*/*;q=0.5

Because these strings are not identical, a strict forward proxy treating the entire Accept string as part of the cache key will store separate instances of the exact same WebP image for each browser type. This leads to:

  • Low Cache Hit Ratios: A WebP image fetched by a Chrome user will not be served from the cache to a Firefox user, even though both support WebP.
  • Storage Inefficiency: The proxy retains multiple identical copies of an image payload simply because the requesting agents formatted their capability strings differently.

Proxy Handling Strategies and Normalization

Modern forward caching proxies employ specific techniques to resolve fragmentation while respecting content negotiation:

1. Header Normalization

Advanced proxies normalize the Accept header before performing the cache lookup. The proxy parses the incoming Accept header to detect whether image/webp is present. Internally, the proxy maps the complex string to a simplified internal flag (e.g., has_webp=true or has_webp=false). The secondary cache key is then generated using this normalized value rather than the raw header string, ensuring that all WebP-capable browsers share the same cached object.

2. Strict RFC Compliance

Standard or legacy forward proxies implement strict RFC 9111 rules without normalization. In these setups, any variation in whitespace, MIME type order, or quality values (q=) in the Accept header results in a distinct cache entry.

3. Handling Proxies That Ignore Vary

If a forward proxy is misconfigured or ignores the Vary header altogether, it uses only the URL as the cache key. This introduces the risk of cache poisoning:

  • If the first visitor supports WebP, the proxy caches the WebP payload. A subsequent visitor using a legacy browser requesting the same URL will receive the cached WebP file, resulting in a broken image display.
  • If the first visitor does not support WebP, the proxy caches the fallback JPEG/PNG, depriving subsequent modern browsers of the bandwidth savings of WebP.

Best Implementation Practices

To ensure forward caching proxies handle dynamic WebP delivery reliably:

  • Always Send Vary: Accept: The origin server must attach this header to both the WebP response and the fallback image response.
  • Combine with Appropriate Cache-Control Directives: Explicit max-age directives guide proxies on how long individual variants remain valid.
  • Consider URL-Based Rewriting: For environments where forward proxies cannot be configured to normalize Accept headers, serving image formats via explicit file extensions or query parameters (e.g., image.webp vs. image.jpg) bypassed content negotiation altogether, eliminating Vary-induced fragmentation.
