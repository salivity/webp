History of libwebp Security Vulnerabilities

Google's WebP image format and its underlying reference implementation, libwebp, are integral components of modern web rendering engines, operating systems, and application frameworks. Because the library is written in C and processes untrusted complex image data, it has historically been targeted by researchers and threat actors looking for memory corruption flaws. Over the years, libwebp has experienced severe security issues, ranging from integer overflows to critical heap buffer overflows capable of remote code execution.

CVE-2023-4863: The Critical Huffman Coding Heap Overflow

The most prominent vulnerability in the library's history is CVE-2023-4863, discovered in September 2023. Initially miscategorized as a vulnerability in Google Chrome, it was quickly identified as an issue residing within the BuildHuffmanTable function in libwebp's lossless compression implementation (VP8L).

When decoding compressed images, the function allocates memory for Huffman tables based on expected symbol counts. An attacker could craft a malformed WebP image with specific bitstream configurations that caused an out-of-bounds write to the allocated heap buffer. Because this library is embedded in nearly every major web browser (Chrome, Firefox, Safari, Edge), communication apps (Signal, Discord, Teams), and operating system components, this zero-day vulnerability presented a massive attack surface. It was exploited in the wild to deliver commercial spyware, achieving arbitrary code execution simply by having an application parse a maliciously constructed image.

Integer Overflows and Sizing Errors

Prior to 2023, several integer overflow vulnerabilities affected the library's chunk and canvas parsing routines. When handling large or corrupted dimensions, math operations responsible for calculating total buffer sizes could overflow, wrapping around to a small positive integer.

For instance, CVE-2020-36330 and CVE-2020-36331 involved scenarios where chunk size calculations overflowed, leading libwebp to allocate a buffer far smaller than the data contained in the payload. When the decompression routine copied the pixel data into this memory, it triggered an out-of-bounds heap write. Similar issues, such as CVE-2020-36332, involved integer overflows during memory allocation for canvas transformation buffers.

Out-of-Bounds Reads and Denial of Service

Extensive continuous fuzzing, notably via Google's OSS-Fuzz project, uncovered a cluster of out-of-bounds read vulnerabilities, such as CVE-2018-25010 through CVE-2018-25014. These bugs typically resided within the code responsible for processing non-standard or truncated alpha channels, advanced prediction filters, and VP8/VP8X transformation headers.

While less severe than heap writes, these out-of-bounds read flaws routinely caused application crashes resulting in Denial of Service (DoS). In some contexts, reading uninitialized or adjacent memory spaces could expose sensitive application data to an attacker.

Structural and Supply Chain Implications

The history of vulnerabilities in libwebp illustrates the risks associated with parsing complex binary file formats in memory-unsafe languages. Because image decompression relies on performance-critical bitwise manipulation and raw pointer arithmetic, even minor boundary miscalculations can lead to exploitable bugs.

Furthermore, the widespread static linking of libwebp across hundreds of software libraries, Electron apps, and package managers created severe supply chain patching delays. Even after Google patched issues upstream, downstream applications often remained vulnerable for months, demonstrating the lingering operational impact of vulnerabilities within fundamental media-parsing libraries.
