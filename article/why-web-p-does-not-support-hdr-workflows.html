Why WebP Does Not Support HDR Workflows

WebP lacks native support for High Dynamic Range (HDR) workflows primarily because it was designed around legacy video compression standards engineered exclusively for 8-bit Standard Dynamic Range (SDR) content. While WebP remains an efficient format for standard web imagery, its underlying architecture cannot accommodate the higher bit depths, modern transfer functions, and wide color gamuts essential for true HDR pipelines. Consequently, the industry has turned toward newer image formats rather than overhauling WebP's aging technical foundation.

Built on an 8-Bit Foundation (VP8)

The primary obstacle preventing native HDR in WebP is its core compression technology. Lossy WebP is derived directly from the VP8 video codec, introduced in 2008. VP8 is architecturally constrained to an 8-bit depth (256 tonal values per color channel) using a YUV 4:2:0 color sampling format.

HDR workflows demand a minimum of 10-bit or 12-bit color depth (1,024 to 4,096 levels per channel). Attempting to display high-luminance, high-contrast HDR data within an 8-bit envelope results in severe color banding and posterization artifacts. Because VP8 lacks the mathematical framework to compress or decode higher bit depths, WebP cannot store HDR imagery natively.

Absence of Modern HDR Metadata and Signaling

Standard HDR delivery relies on specific electro-optical transfer functions (EOTFs) and wide color primaries, notably:

  • Perceptual Quantizer (PQ / SMPTE ST 2084)
  • Hybrid Log-Gamma (HLG)
  • BT.2020 and Display P3 wide color gamuts

Modern formats handle these parameters efficiently via Coding-Independent Code Points (CICP) or NCLX color metadata tags. While the WebP container format (an extended RIFF structure) allows for embedded ICC profiles and EXIF metadata, it does not have standard, hardware-level signaling for PQ or HLG curves. Relying solely on large, embedded ICC profiles for color transformation is computationally expensive, poorly supported across web hardware acceleration layers, and inadequate for luminance scaling above standard SDR levels.

Limited Scope of the Original Specification

When Google introduced WebP in 2010, the primary goal was reducing payload size across the web to decrease page load times on standard sRGB displays. HDR displays were non-existent in consumer web browsing environments at the time. As a result, the specification prioritized low computational overhead, rapid decoding in web browsers, and backward compatibility over forward-looking display technologies.

Industry Shift to AVIF

Rather than re-engineering WebP to support 10-bit color, wide gamuts, and HDR signaling—which would have created a format completely incompatible with existing WebP decoders—the industry pivoted toward formats derived from modern codecs.

Formats like AVIF (based on the AV1 video codec) were designed with native 10-bit and 12-bit encoding, full support for BT.2020 primaries, and native integration with PQ and HLG transfer functions. Because AVIF and other modern alternatives natively solve the HDR challenge with superior compression efficiency, development on extending WebP to HDR workflows was effectively abandoned.
