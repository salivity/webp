WebP Support in FreeDesktop Icon Specification

This article examines how the FreeDesktop.org standards interact with modern WebP graphics, detailing the limitations of the official Icon Theme Specification, how desktop environments handle WebP assets in practice, and the current workarounds for application developers. While the formal specification does not natively include WebP within standard theme resolution algorithms, the broader desktop ecosystem accommodates WebP assets through toolkit decoders and explicit desktop entry pathways.

The Formal Icon Theme Specification

The official FreeDesktop.org Icon Theme Specification defines how Linux and Unix-like desktop environments locate and render icons. According to the specification, the recognized image formats are strictly limited to:

  • SVG (and compressed SVGZ) for scalable vector graphics.
  • PNG for raster graphics across defined resolutions.
  • XPM retained purely for backward compatibility with legacy applications.

When a desktop environment searches for an icon by name (for example, firefox), the specification outlines an exact lookup algorithm that appends file extensions in order of preference (.png, .svg, .xpm). Because .webp is not listed in this standard lookup sequence, theme engines and desktop shells adhering strictly to the FreeDesktop specification do not automatically parse or display WebP files placed inside standard icon theme directories (such as /usr/share/icons/hicolor/).

Accommodating WebP via Desktop Entry Files

Although WebP is omitted from standard theme directory lookups, the FreeDesktop.org Desktop Entry Specification offers a mechanism to use WebP assets.

In a standard .desktop launcher file, the Icon key accepts either an icon name (which invokes the theme lookup algorithm) or an absolute file path:

  • Themed Name (No WebP): Setting Icon=myapp instructs the shell to search registered icon themes for myapp.png or myapp.svg.
  • Direct Path (WebP Supported): Setting Icon=/usr/share/pixmaps/myapp.webp bypasses theme lookup completely.

When an absolute path is used, the desktop shell directly passes the target file to the rendering pipeline of its underlying GUI toolkit.

The Role of Desktop Toolkits

Actual rendering of a WebP graphic depends on the graphical libraries used by the desktop environment:

  • GTK / GNOME: GTK relies on gdk-pixbuf to load image formats. If the webp-pixbuf-loader library is installed, GTK-based environments can decode and display WebP icons referenced by path.
  • Qt / KDE Plasma: Qt uses an image formats plugin system. With the qt5-imageformats or qt6-imageformats package installed, KDE Plasma can display WebP icons.

If the appropriate loader is present on the host system, the desktop environment will render the WebP graphic in application launchers, taskbars, and window switchers without issue.

Practical Implications for Developers

Because WebP is not part of the standard theme resolution order, packaging WebP files inside standard /usr/share/icons/ theme structures can lead to missing icons on systems using strictly compliant desktop components or lacking third-party WebP loaders.

To ensure maximum compatibility across all Linux distributions, developers targeting FreeDesktop environments typically continue to provide standard PNG files for fixed raster sizes and SVG files for scalable icons. Where reduced package sizes or memory footprints make WebP desirable, developers must reference the asset using an absolute file path and ensure the system provides the required toolkit decoding libraries.
