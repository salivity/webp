How WebP Distinguishes Simple and Extended Headers

The WebP image format relies on the Resource Interchange File Format (RIFF) container structure, which enables decoders to determine an image's underlying features rapidly. The container differentiates between simple and extended file headers by reading the Four-Character Code (FourCC) located at byte offset 12, immediately following the standard 12-byte RIFF header. If this FourCC is VP8 or VP8L, the file uses a simple header for lossy or lossless data, respectively; if the FourCC is VP8X, the file uses an extended header to accommodate advanced features like alpha channels, animations, and metadata.

The RIFF Header Baseline

Every WebP file begins with a mandatory 12-byte RIFF header:

  • Bytes 0–3: The ASCII characters 'RIFF'.
  • Bytes 4–7: A 32-bit little-endian integer indicating the total size of the file minus 8 bytes.
  • Bytes 8–11: The ASCII characters 'WEBP'.

A WebP parser reads these initial 12 bytes to confirm that the file is a valid WebP resource. The distinguishing logic begins immediately after byte 11, where the first chunk header resides.

Identifying Simple Headers (VP8 and VP8L)

A WebP file is classified as having a simple format if the first chunk immediately following the RIFF header is either a lossy or lossless image stream.

  • Lossy WebP (VP8 ): If bytes 12–15 match the FourCC 'VP8 ' (with a trailing space), the parser identifies the file as a basic lossy image. The payload of this chunk directly contains the VP8 bitstream, frame dimensions, and encoded macroblocks.
  • Lossless WebP (VP8L): If bytes 12–15 match the FourCC 'VP8L', the parser treats the file as a basic lossless image. The chunk payload directly contains the VP8L bitstream, which includes the image size and entropy-coded pixel data.

In both simple cases, no additional header layer exists between the container's base header and the raw image bitstream. This minimizes overhead for standard, single-frame images without auxiliary data.

Identifying Extended Headers (VP8X)

When an image requires advanced capabilities beyond a single, basic image frame, the container employs an extended header signified by the FourCC 'VP8X'.

  • Extended WebP (VP8X): If bytes 12–15 match the FourCC 'VP8X', the decoder branches into extended parsing mode.

The VP8X chunk is mandatory for any WebP file that includes:

  • ICC Profiles: Embedded color management data.
  • Alpha Channels: Independent transparency layers paired with lossy VP8 data.
  • EXIF or XMP Metadata: Non-pixel descriptive data.
  • Animation: Multiple frames defined through ANIM and ANMF chunks.

Structure of the VP8X Chunk

When the parser encounters VP8X, it reads a standardized 10-byte payload that defines the global properties of the image canvas:

  1. Reserved Bits and Flags (Bytes 0–3 of the payload): A 32-bit field containing individual bit flags that notify the parser which optional chunks follow later in the file:
    • Bit 1: Animation flag
    • Bit 2: XMP metadata flag
    • Bit 3: EXIF metadata flag
    • Bit 4: Alpha channel flag
    • Bit 5: ICC profile flag
  2. Canvas Width (Bytes 4–6 of the payload): A 24-bit integer representing the canvas width minus one.
  3. Canvas Height (Bytes 7–9 of the payload): A 24-bit integer representing the canvas height minus one.

Summary of Parsing Flow

A WebP decoder differentiates between simple and extended formats through the following sequence:

  1. Validate bytes 0–3 ('RIFF') and bytes 8–11 ('WEBP').
  2. Read the FourCC at byte 12.
  3. If the FourCC is 'VP8 ' or 'VP8L', parse the payload immediately as a single-frame, self-contained simple image stream.
  4. If the FourCC is 'VP8X', parse the canvas dimensions and bit flags, then iterate sequentially through subsequent chunks (such as ICCP, ALPH, VP8, VP8L, EXIF, or XMP ) as indicated by the flags.
