WebP Fallback Workflow for Legacy Browsers

Serving WebP images dramatically reduces payload sizes and improves page load times, but older legacy browsers do not natively support the format. This article outlines the recommended fallback workflow to serve WebP images to modern browsers while reliably delivering legacy formats like JPEG or PNG to unsupported clients. By combining semantic HTML, server-side content negotiation, and CSS feature detection, you can ensure universal compatibility without sacrificing performance.

1. The HTML5 <picture> Element

The most robust and standard client-side method is using the HTML5 <picture> element. It allows you to define multiple source files, letting the browser choose the first format it supports.

<picture>
  <source srcset="image.webp" type="image/webp">
  <img src="image.jpg" alt="Description of the image" loading="lazy">
</picture>

How it works:

  • The browser evaluates the <source> tags from top to bottom.
  • If the browser supports image/webp, it downloads and displays image.webp.
  • If it does not support WebP, or if it is an older browser that does not recognize <picture>, it falls back to the standard <img> tag with the JPEG/PNG source.
  • Attributes like alt, loading, width, and height must always be placed on the nested <img> tag.

2. Server-Side Content Negotiation

If you manage a large legacy codebase or cannot modify HTML markup to use <picture>, server-side content negotiation is the preferred alternative. This approach serves WebP dynamically under the same file URL based on HTTP headers.

Implementation Workflow:

  1. Inspect the Accept Header: When a client requests an image, check if the request header includes image/webp.
  2. Serve the Supported Format:
    • If image/webp is present and a .webp version exists on the server, return the WebP file.
    • If image/webp is missing, return the original .jpg or .png file.
  3. Include the Vary Header: Always send the Vary: Accept response header. This prevents CDNs and intermediate caches from serving a cached WebP image to a legacy browser that subsequently requests the same URL.

3. Handling CSS Background Images

The <picture> element only applies to inline images. For background images defined in CSS, use feature detection via Modernizr or native CSS @supports.

Modernizr Approach: Modernizr runs a small JavaScript check to see if WebP is supported and appends a .webp or .no-webp class to the <html> element.

.hero {
  background-image: url("hero.jpg");
}

.webp .hero {
  background-image: url("hero.webp");
}

CSS @supports Approach: For browsers that support modern CSS features, you can check format decoding directly in stylesheets:

.hero {
  background-image: url("hero.jpg");
}

@supports (background-image: url("test.webp")) {
  .hero {
    background-image: url("hero.webp");
  }
}

4. Build-Time Asset Generation

A seamless fallback workflow requires automating image generation during your build step:

  • Keep original, high-resolution source files (PNG or TIFF) in your source directory.
  • Use tools like Sharp, ImageMin, or Webpack/Vite plugins to simultaneously generate optimized WebP and fallback JPEG/PNG variants.
  • Maintain identical dimensions, aspect ratios, and naming conventions (e.g., banner.webp and banner.jpg) to prevent layout shifts.
