How the WebP Lossless Color Cache Works

The WebP lossless image format relies on several advanced encoding techniques to achieve superior compression ratios compared to traditional formats like PNG, with the color cache mechanism being one of its most critical components. This article explains how the dynamic color cache functions within WebP lossless compression, the mathematical hashing process it uses to track recently seen colors, and how referencing this cache directly reduces image file sizes.

The Purpose of the Color Cache

In graphic assets, user interface elements, and illustrations, identical colors often repeat frequently across an image, but not always in continuous spatial sequences that standard run-length or dictionary-based algorithms (like LZ77) can easily capture.

While indexed formats like GIF or 8-bit PNG use a fixed global palette, WebP lossless compression employs a dynamic, localized color cache. This mechanism allows the encoder to reference recently used colors with a very small index code, bypassing the need to repeatedly store full 32-bit ARGB values or search through large backward-reference windows.

How the Cache Operates

The color cache is a fixed-size array of recently observed ARGB pixel values. The size of the cache is always a power of two, defined by a parameter called color_cache_bits, which ranges from 1 to 11. Consequently, the cache capacity ranges from 2 (\(2^1\)) to 2,048 (\(2^{11}\)) color entries.

Unlike conventional Least Recently Used (LRU) caches that require complex pointer updates, WebP uses a deterministic hash lookup. When an ARGB color needs to be stored or retrieved, its slot in the cache is calculated using a multiplicative hashing function:

\[\text{Index} = (0x1e35a7bd \times \text{ARGB}) \gg (32 - \text{color\_cache\_bits})\]

Because the index calculation relies solely on the ARGB value itself, both the encoder and decoder can independently maintain identical cache states without exchanging index-mapping tables.

The Encoding and Decoding Process

During compression, the encoder processes pixels sequentially and evaluates the cache:

  1. Lookup: The encoder computes the hash index of the current pixel's ARGB value.
  2. Comparison: If the color stored at that hash index matches the current pixel, a cache hit occurs.
  3. Emission: Instead of emitting a literal ARGB value or an LZ77 distance/length pair, the encoder outputs an index token pointing directly to the cache slot.
  4. Update: If there is a cache miss, the pixel is encoded via literals or backward references, and the new color is placed into the cache at its calculated hash index, overwriting any previous color stored in that slot.

Because the decoder processes the stream in the exact same order, it applies the identical hash function and continuously updates its local cache alongside the encoder.

Integration with Entropy Coding

WebP lossless encodes literals, LZ77 copy lengths, and color cache indices into a single unified alphabet. The alphabet consists of:

  • 256 Green literal values
  • Variable-length LZ77 copy codes
  • Color cache codes (ranging from 0 up to \(2^{\text{color\_cache\_bits}} - 1\))

By integrating cache indices directly into this single prefix-coded (Huffman) alphabet, the most frequently referenced cache slots receive the shortest bit-lengths, maximizing entropy coding efficiency.

Advantages of the Mechanism

The dynamic color cache provides substantial compression advantages over traditional static palettes. It requires zero file overhead to transmit a predefined palette at the start of the file, adapts seamlessly to local color shifts throughout large images, and complements LZ77 compression by efficiently handling colors that reappear outside the backward-reference window.
