Parsing ICC Profile Chunks in Extended WebP

Extended WebP files rely on the Resource Interchange File Format (RIFF) container to store advanced features like color management, transparency, and animation alongside image data. Identifying and parsing an International Color Consortium (ICC) profile within these files requires checking the feature flags in the extended WebP header (VP8X) and extracting the raw profile data from the dedicated ICCP chunk. This process allows image decoders to correctly interpret color spaces and render colors accurately across various display devices.

1. Validating the Container and Extended Header

WebP files are encapsulated in a standard RIFF wrapper. A parser begins by reading the first 12 bytes of the file to verify the signature:

  • Bytes 0–3: The ASCII string "RIFF".
  • Bytes 4–7: A 32-bit little-endian integer indicating the total file size minus 8 bytes.
  • Bytes 8–11: The ASCII string "WEBP".

For an ICC profile to exist, the file must be formatted as an Extended WebP. In this case, the first chunk directly following the 12-byte container header must be a VP8X chunk.

The parser reads the VP8X chunk:

  • Chunk FourCC (4 bytes): "VP8X"
  • Chunk Size (4 bytes): Always 10 for VP8X (representing 10 bytes of payload).
  • Payload Flags (1 byte): The first byte of the VP8X payload contains feature flags. The parser performs a bitwise check on this byte. Bit 5 (represented by the mask 0x20) is the ICC profile flag. If this bit is set to 1, an ICC profile chunk is present in the file. If it is 0, the parser skips searching for an ICC profile.

2. Locating the ICCP Chunk

Once the presence of the ICC profile is confirmed by the VP8X flag, the parser iterates through the subsequent RIFF chunks to find the profile data. According to the WebP specification, the ICCP chunk must appear before the primary image data chunks (VP8, VP8L, or ANIM).

The parser advances past the VP8X chunk (its 8-byte header plus 10-byte payload) and reads chunks sequentially until it encounters the FourCC identifier "ICCP".

3. Reading and Parsing the ICCP Chunk

When the "ICCP" FourCC is matched, the chunk is parsed as follows:

  1. Chunk Identifier (4 bytes): Confirmed as the ASCII sequence "ICCP".
  2. Chunk Size (4 bytes): A 32-bit unsigned integer stored in little-endian byte order. This value denotes the exact length, in bytes, of the ICC profile payload that follows.
  3. Payload (Variable length): Exactly Chunk Size bytes of data representing the raw ICC profile. Unlike formats like PNG, WebP does not compress the ICC profile payload with zlib or prepend a profile name string; it stores the uncompressed binary ICC profile directly.
  4. RIFF Padding (0 or 1 byte): The RIFF specification requires every chunk to be aligned to an even byte boundary. If the Chunk Size is an odd number, the chunk is followed by a single padding byte (0x00). This padding byte is not counted in the Chunk Size value, but the parser must advance past it to locate any subsequent chunks correctly.

4. Consuming the Extracted Profile

Once the raw payload bytes are extracted, the parser hands the data off to a color management system (CMS), such as LittleCMS or an operating-system-level color engine. The CMS verifies the internal 128-byte header of the ICC data—validating standard markers such as the profile size, color space signature (e.g., "RGB "), and the magic signature "acsp"—allowing the host application to apply accurate color transformations to the decoded image pixels.
