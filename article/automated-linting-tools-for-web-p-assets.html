Automated Linting Tools for WebP Assets

Serving modern image formats like WebP is essential for optimizing web performance, improving Core Web Vitals, and maintaining strong search engine rankings. This article explores the automated linting tools, CI/CD integrations, and static analysis workflows available to verify that all public assets on a website have corresponding WebP equivalents before or during deployment.

Lighthouse CI (LHCI)

Lighthouse CI is the industry standard for auditing web page assets in continuous integration pipelines. It includes an explicit audit for "Serve images in next-gen formats," which flags JPEG or PNG assets that could yield significant byte savings if converted to WebP or AVIF.

To enforce WebP equivalents across your public pages:

  • Install @lhci/cli in your project.
  • Configure an assertion rule inside .lighthouserc.json targeting modern-image-formats.
  • Set the assertion level to error to break the build whenever an asset is served without a modern format equivalent.

LHCI operates against built production code, making it an effective end-to-end verification step.

html-validate

For static sites and template-driven architectures, html-validate is a standalone HTML linter that checks the rendered or template output. While it focuses primarily on HTML standards and accessibility, its rule configuration and plugin architecture allow developers to enforce specific markup patterns, such as requiring <picture> wrappers with WebP <source> elements instead of standalone <img> tags.

You can create custom rules in html-validate to:

  • Ensure every <img> referencing a legacy extension (.jpg, .png) is nested inside a <picture> element.
  • Verify that an adjacent <source type="image/webp"> exists pointing to the corresponding WebP version.

Pre-Commit and Static Directory Linters

When assets live in a static directory (such as /public, /static, or /assets), static file-system linters provide the fastest feedback loop by validating assets before compilation occurs.

Custom Node.js / Glob Linters

Because standard linters often ignore binary assets, many teams implement custom scripts using glob or fast-glob as a pre-commit or pre-build step. A standard static check:

  1. Scans the public directory for all .png and .jpg/.jpeg files.
  2. Checks if a file with the same base name and a .webp extension exists in the same path.
  3. Exits with process code 1 and lists missing WebP files if discrepancies are found.

lint-staged Integration

Pairing a custom asset verification script with lint-staged and husky ensures that developers cannot commit a raster image without also committing its WebP equivalent, catching unoptimized assets at the developer environment level.

Framework-Specific ESLint Plugins

Modern frameworks often manage image optimization and asset serving directly through dedicated components. Automated linting can be applied to verify image usage:

  • Next.js (@next/next): The @next/next/no-img-element rule prevents using raw HTML <img> elements, forcing the use of the next/image component. Next.js handles WebP generation dynamically or verifies static imports at build time.
  • Nuxt and SvelteKit: Similar ecosystem linters enforce the use of @nuxt/image or @sveltejs/enhanced-img, which perform build-time validation to verify that modern formats exist or are generated automatically during the build process.

Playwright / Puppeteer Network Scrapers

For dynamically rendered sites, headless browser suites like Playwright or Puppeteer can serve as automated integration linters. A simple CI test script can navigate through all published sitemap URLs, intercept network requests, and assert that every requested image asset either delivers image/webp content or includes an alternative WebP candidate in the DOM's srcset attributes.
