How File Explorers Generate WebP Thumbnails

Desktop operating systems rely on background rendering architectures, platform-native image decoders, and modular plugin frameworks to generate WebP image previews in their file explorers. While WebP is an open, modern image format developed by Google, desktop file managers like Windows File Explorer, macOS Finder, and Linux file managers (such as Nautilus or Dolphin) do not directly render images themselves. Instead, they query underlying graphics frameworks, dedicated thumbnailing services, and cached databases to convert WebP data into preview icons.

Windows: The Windows Imaging Component and Shell Extensions

Microsoft Windows generates thumbnails for File Explorer primarily through the Windows Imaging Component (WIC) and the IThumbnailProvider Component Object Model (COM) interface.

Modern versions of Windows 10 and Windows 11 include or dynamically install the "WebP Image Extension" via the Microsoft Store. This extension acts as a WIC codec, wrapping the reference libwebp decoding library. When a user opens a folder containing WebP files, File Explorer executes the following steps:

  1. Querying the Registry: The shell checks the Windows Registry under the .webp file association for an assigned ThumbnailHandler CLSID pointing to an IThumbnailProvider implementation.
  2. Decoding the Stream: The registered provider invokes the WIC WebP decoder, reading the file header to determine dimensions, color profile, and compression type (lossy VP8 or lossless VP8L).
  3. Bitmap Extraction: The decoder extracts the pixel data—taking the first frame in animated WebP files—and renders it to an in-memory device-independent bitmap (DIB).
  4. Caching: The generated bitmap is scaled to the requested icon size (e.g., 96x96, 256x256) and saved in the centralized Windows thumbnail cache (thumbcache_*.db) located in the user's AppData directory to prevent redundant decoding.

macOS: ImageIO and Quick Look

macOS Finder handles WebP thumbnail generation through the system-level ImageIO framework and the Quick Look service.

Starting with macOS 11 (Big Sur), Apple added native system-level decoding for WebP directly into ImageIO and Core Graphics. The process operates as follows:

  1. File Inspection: Finder reads the file's Uniform Type Identifier (UTI), identifying it as org.webmproject.webp (or public.webp).
  2. Quick Look Thumbnailing Service: The operating system passes the file path to quicklookd, a background daemon that handles preview creation.
  3. Core Graphics Pipeline: quicklookd uses ImageIO's CGImageSource API to parse the WebP data stream. The framework extracts the visual payload using Apple's built-in codec, applies proper color space matching, and downsamples the image to an off-screen CGImage buffer.
  4. Cache Storage: The rendered thumbnail is stored inside the macOS Quick Look cache database (/var/folders/.../C/com.apple.QuickLook.thumbnailcache) for instantaneous retrieval in future Finder views.

On legacy macOS versions lacking native support, third-party .qlgenerator bundles fulfilled this role by interfacing directly with Quick Look APIs and a statically linked version of libwebp.

Linux: The FreeDesktop.org Thumbnail Standard

Linux desktop environments (including GNOME, KDE Plasma, and XFCE) follow the unified FreeDesktop.org Thumbnail Managing Standard to generate WebP previews.

Instead of monolithic system APIs, Linux uses modular background thumbnailer daemons such as tumbler or desktop-specific thumbnail services:

  1. MIME-Type Matching: The file manager detects the MIME type image/webp via the system MIME database.
  2. Thumbnailer Invocation: The file manager searches /usr/share/thumbnailers/ for a .thumbnailer configuration file associated with image/webp. This configuration specifies a command-line executable (such as gdk-pixbuf-thumbnailer, gnome-desktop-thumbnailer, or an ImageMagick-based utility).
  3. Decoding Libraries: The invoked executable decodes the WebP file. In GNOME-based environments, this is commonly handled by gdk-pixbuf combined with the webp-pixbuf-loader plugin. In KDE environments, the kio-extras framework employs Qt's image format plugins compiled with libwebp support.
  4. Storage: The decoded image is downscaled to standard sizes (normal at 128x128 pixels, large at 256x256, or extra-large at 512x512) and saved as a PNG file inside the user's local cache directory at ~/.cache/thumbnails/, named using an MD5 hash of the original file's URI.
