Fallback Open Graph Images for WebP Assets

While modern image formats like WebP significantly reduce bandwidth on websites, social media crawlers and messaging platforms frequently fail to render them when scraping Open Graph metadata. Web developers must implement reliable fallback strategies to ensure link previews display properly across platforms like Facebook, LinkedIn, X, and WhatsApp without sacrificing the performance benefits of WebP on the actual page. This guide covers how to structure meta tags, leverage format fallbacks, and use server-side negotiation to serve the right image format to both browsers and social scrapers.

The Problem with WebP and Social Crawlers

Web browsers widely support WebP, but social media platforms rely on automated scrapers (such as facebookexternalhit or Twitterbot) that use older image processing pipelines. Many of these crawlers do not decode WebP or AVIF formats. If an og:image tag points exclusively to a WebP asset, the shared link often displays a broken preview or no image at all.

Strategy 1: Declare Universal Formats in Open Graph Tags

The most straightforward approach is to decouple your on-page web assets from your Open Graph assets. While your page content can use WebP inside modern <picture> elements, your Open Graph tags should prioritize a universally supported format like JPEG or PNG.

<!-- On-page content uses modern formats -->
<picture>
  <source srcset="/images/hero.webp" type="image/webp">
  <img src="/images/hero.jpg" alt="Hero representation" />
</picture>

<!-- Open Graph metadata uses fallback formats -->
<meta property="og:image" content="https://example.com/images/share.jpg" />
<meta property="og:image:secure_url" content="https://example.com/images/share.jpg" />
<meta property="og:image:type" content="image/jpeg" />
<meta property="og:image:width" content="1200" />
<meta property="og:image:height" content="630" />

Because social preview images are only downloaded when a link is shared, using a high-quality, properly compressed JPEG (typically around 1200x630 pixels and under 300KB) avoids crawler compatibility issues without impacting initial page-load metrics for regular users.

Strategy 2: Array-Based Open Graph Declarations

The Open Graph protocol allows developers to define multiple image tags as an array. When doing this, order and explicit MIME types matter.

Some platforms parse through the list until they find a MIME type they support. When declaring an array, you can declare the WebP version first, followed immediately by the fallback JPEG or PNG:

<!-- Primary WebP Option -->
<meta property="og:image" content="https://example.com/images/share.webp" />
<meta property="og:image:type" content="image/webp" />
<meta property="og:image:width" content="1200" />
<meta property="og:image:height" content="630" />

<!-- Fallback JPEG Option -->
<meta property="og:image" content="https://example.com/images/share.jpg" />
<meta property="og:image:type" content="image/jpeg" />
<meta property="og:image:width" content="1200" />
<meta property="og:image:height" content="630" />

Note: Some aggressive parsers stop at the very first og:image tag they encounter. If that tag points to an unsupported WebP file, they will fail to process the fallback. If broad compatibility is your highest priority, reverse the order or default strictly to JPEG/PNG in your metadata.

Strategy 3: Dynamic Server-Side Content Negotiation

If you prefer using a single URL for all preview assets (for example, https://example.com/og-image), you can handle format negotiation on the server or via edge functions.

  1. Check the Accept Header: If a client explicitly includes image/webp in the Accept header, return the WebP asset with a Content-Type: image/webp header.
  2. Check the User-Agent: Identify known social media bots (e.g., facebookexternalhit, LinkedInBot, Twitterbot, Slackbot) and force-serve a JPEG or PNG response regardless of requested formats.
  3. Include the Vary: Accept Header: Ensure your caching layer (like a CDN) caches separate versions for different Accept headers to prevent serving WebP to crawlers that cannot parse it.

Testing and Validation

Once fallback tags or dynamic endpoints are deployed, validate the output using official preview tools:

  • Facebook Sharing Debugger: Clears the platform's cache and shows the exact extracted image.
  • X Card Validator: Verifies how the link card renders.
  • LinkedIn Post Inspector: Displays parsed metadata and indicates format-related scraping errors.
