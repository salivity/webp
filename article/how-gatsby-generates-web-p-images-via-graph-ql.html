How Gatsby Generates WebP Images via GraphQL

This article explains how Gatsby automates WebP image generation during its static build process. By leveraging its image processing ecosystem—primarily gatsby-plugin-image, gatsby-plugin-sharp, and gatsby-transformer-sharp—Gatsby intercepts local and remote media sourced into its GraphQL data layer. It transforms standard formats like JPEG and PNG into modern WebP variants at build time and structures the data to ensure optimal delivery and backward-compatible rendering in the browser.

The Underlying Plugin Architecture

Gatsby’s media processing does not happen natively within the core framework; instead, it relies on a coordinated set of plugins:

  1. gatsby-source-filesystem: Scans specified directories on the local machine or remote nodes, converting file assets into File nodes in the GraphQL schema.
  2. gatsby-transformer-sharp: Recognizes supported image media types on File nodes and attaches child ImageSharp nodes to the GraphQL schema.
  3. gatsby-plugin-sharp: Acts as the low-level processing engine. It exposes configuration APIs and directly interfaces with the high-performance C library libvips through the Node.js sharp package.

Querying WebP in the GraphQL Layer

Developers define image transformation requirements directly within GraphQL queries using the gatsbyImageData resolver. This resolver accepts arguments that govern output formats, resizing dimensions, and quality levels.

By default, modern Gatsby configurations include WebP automatically when querying gatsbyImageData. Developers can also explicitly set the output formats:

query {
  file(relativePath: { eq: "hero.jpg" }) {
    childImageSharp {
      gatsbyImageData(
        layout: CONSTRAINED
        placeholder: BLURRED
        formats: [AUTO, WEBP]
      )
    }
  }
}

In this query, AUTO maintains the original source format (e.g., JPEG or PNG), while WEBP explicitly instructs the pipeline to generate a WebP counterpart.

Build-Time Processing and Static Asset Generation

When you execute gatsby build, the framework orchestrates the transformation:

  1. Query Extraction and Analysis: Gatsby extracts all GraphQL queries across pages and components, aggregating image transformation instructions into an internal processing queue.
  2. Sharp Transformation via libvips: For every requested resolution and density (such as 1x, 2x for retina displays), gatsby-plugin-sharp invokes sharp. The engine reads the source image buffer, scales it, converts the pixel data to WebP encoding, and compresses it according to specified or default quality settings.
  3. Static Output: The newly generated .webp files, along with fallback images, are written directly to the /public/static/ folder with content-hashed filenames for immutable caching.
  4. Data Object Emission: The GraphQL query returns an optimized JSON payload containing metadata: image dimensions, srcsets for both WebP and fallback formats, and placeholder strings (such as base64-encoded blurs or SVG traces).

Client-Side Execution and Fallbacks

Because older browsers or edge-case environments may lack WebP support, Gatsby ensures fallback compatibility via the <GatsbyImage /> React component.

The component consumes the data payload provided by the GraphQL query and renders a native HTML5 <picture> element:

<picture>
  <source 
    type="image/webp" 
    srcset="/static/hash-1x.webp 1x, /static/hash-2x.webp 2x" 
  />
  <source 
    type="image/jpeg" 
    srcset="/static/hash-1x.jpg 1x, /static/hash-2x.jpg 2x" 
  />
  <img 
    src="/static/hash-1x.jpg" 
    loading="lazy" 
    decoding="async" 
    alt="Hero Image" 
  />
</picture>

The browser evaluates the <picture> tag sequentially. If the client supports the WebP MIME type, it downloads and displays the WebP asset from the first <source> element. If not, it falls through to the original format fallback, ensuring automated performance optimization without sacrificing compatibility.
